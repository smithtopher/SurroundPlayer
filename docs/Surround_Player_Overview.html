Surround Player

A music and video player for macOS and Windows 11 that plays surround sound over HDMI as a compressed Dolby Digital or DTS bitstream (IEC 61937), modelled on Kodi's WASAPI-exclusive passthrough.

1 · The problem: why a bitstream, and why it is hard

The user's playback chain is computer → HDMI → Samsung TV → optical (S/PDIF) → AC3-capable amp. The last link decides everything. Optical S/PDIF carries only two channels of PCM. It cannot carry 5.1 PCM. A stock player sends decoded multichannel PCM over HDMI; the TV then downmixes it to stereo for the optical port, and the amp never sees surround.

The way through is to send the surround audio still compressed, as Dolby Digital (AC3) or DTS, wrapped so that it looks like a stereo 48 kHz PCM stream (IEC 61937). The TV in pass-through mode forwards those bits unchanged, and the amp decodes the 5.1 itself.

Why it is hard

  • Every bit must arrive untouched. The OS mixer, volume, resampling, dither or any effects processing would corrupt the bitstream and turn it into loud noise. The player has to take the device for itself (CoreAudio hog mode with mixing off; WASAPI exclusive mode).
  • The receiver must stay locked. If the stream stops or a burst is torn, the amp drops out of Dolby Digital and takes up to a second to re-lock. So the player sends encoded silence while paused, seeking or between tracks, and only switches between real data and silence on burst boundaries.
  • Most sources aren't AC3. AAC, FLAC, E-AC3, TrueHD and DTS-HD tracks have to be decoded and re-encoded to AC3 or DTS on the fly.
  • Video must follow audio. With a large ring buffer and an amp that adds decode delay, the picture has to be timed against what is actually leaving the device, not against wall time.
  • Bitstreaming the wrong device is dangerous. IEC 61937 data played on speakers or headphones is full-scale noise.
Why model it on Kodi? Kodi's WASAPI-exclusive passthrough is a proven design for exactly this problem. The project maps each Kodi building block onto CoreAudio (and later back onto WASAPI): exclusive stream, no mixer, IEC 61937 subtype, ActiveAE transcoding, CAEPackIEC61937, keep-alive silence and a sink kept open across tracks.

2 · IEC 61937 in one page

IEC 61937 is how compressed audio travels over interfaces built for PCM (S/PDIF, HDMI). Each compressed frame becomes a burst: a short preamble, the frame itself, then zero padding. The burst is exactly as long as the PCM the frame would decode to (2 channels × 16 bit × the frame's sample count), so the link runs at the normal 48 kHz stereo rate. Only the receiver knows it isn't audio.

3 · Architecture: portable core and per-OS back-ends

The repo is one C engine shared by two native apps. The engine was deliberately split so that everything hard (decoding, encoding, IEC 61937, burst logic, clock, sync) is portable C with no OS media code. Each OS supplies two small back-ends that only own the device.

Why this split? The rule is "back-ends own only the device". All IEC 61937, keep-alive and clock logic lives in the portable render() callback, so it is written and debugged once. That paid off on Windows: pc_platform.h's Win32 branch compiled unchanged, and regress.sh printed ALL PASSED with the stub back-ends before any device code existed. check_portable.sh enforces the rule on every macOS run by building the core against the stubs and failing on any OS media header or symbol.
Opaque native frames. PCNativeFrame is a CVPixelBufferRef on macOS and a D3D11 texture-array slice (or BGRA CPU frame) on Windows. The core never looks inside; the UI does, so frames go from the GPU decoder to the screen without a copy.

4 · Inside the engine: threads and data flow

A player instance runs four threads plus the device's real-time callback. Queues decouple them, so a slow decode never blocks the device, and a seek bumps a serial number that makes every stage drop stale data.

Why a lock-free ring? render() runs on the OS's real-time audio thread. It must never block on a lock held by a decoder, or the device underruns and the amp loses lock. Positions are atomics; the ring is single-producer, single-consumer.
Why keep the output open? Between files, the output is reused (kept_out) when device, mode and burst size match. The amp stays locked to Dolby Digital, so the next track starts without a dropout.

5 · Choosing what to send: the mode decision

For each file the engine picks one of three output modes (PCOutputMode): PCM (shared mode), TRANSCODE (decode and re-encode) or PASSTHROUGH (the source's own packets). The choice follows the user's "Surround output" setting and the source track.

Why does Dolby Digital mode transcode DTS? Not every amp, and not every TV's optical pass-through, handles DTS. AC3 is the safe common denominator, so DD mode turns everything into AC3.
Why is stereo PCM by default? Stereo gains nothing from AC3, and encoding costs quality. "Also encode stereo sources" exists for amps that drop audio for a moment when switching between PCM and a bitstream.
Fallbacks are real, not theoretical. On the Windows PC, the Samsung's HDMI endpoint refuses the IEC 61937 DTS subtype (its EDID lists no DTS), so DTS mode falls back to decoded PCM there. The back-end deliberately has no PCM-container fallback for bitstreams; it fails the open and the engine chooses PCM.

6 · The render callback: whole bursts and keep-alive silence

render(ctx, dst, frames, present_ns) in pc_output.c is the heart of the output. The OS calls it on its real-time thread whenever it needs frames more samples. In bitstream mode it is a small state machine that guarantees the receiver only ever sees complete bursts, real or silent.

Timeline: pause and seek while playing Dolby Digital

Why not just output zeros when paused? Zeros aren't a valid IEC 61937 stream. The receiver falls back to PCM, then needs time to re-detect Dolby Digital on resume, which clips the start of the audio and makes the amp click between modes. Encoded silence keeps it locked.

A flush (seek) is signalled through an atomic generation counter: the writer advances a flush target, render() notices the new generation, jumps its read position forward and finishes the current burst as silence. No lock is ever taken on the real-time thread.

7 · The clock and A/V sync

Audio is the master clock. Video, the visualiser and the position display all follow what is actually leaving the audio device. Because there is a ring buffer, device buffering and an amp that decodes AC3, "now" for the listener is well behind what the decoder just produced.

Why pts markers instead of counting samples? In bitstream mode the ring holds IEC bursts, not samples, and in passthrough the bursts come from the source's packets. Tagging ring byte positions with the source pts works the same for PCM, transcode and passthrough, and survives seeks: a seek simply starts a new run of markers.
Why a seqlock? The record is written on the real-time thread and read by the presenter and UI. A seqlock lets the reader retry on a torn read, and the writer never waits.

The visualiser tap uses the same clock: decoded audio (stereo float, 48 kHz, with pts markers) is read for the current clock position, so the visuals line up with what is audible, even while bitstreaming, and they follow the Audio latency setting just like video.

Video

Why share the UI's D3D11 device? pc_set_d3d11_device is called before open, so decoded textures are created with SHADER_RESOURCE on the same device the UI renders with. The pixel shader samples them directly, with no copy or cross-device sharing. The decoder pool is enlarged by 10 frames to cover the engine's frame queue.

On the Windows test PC (GTX 970) there is no hardware HEVC, so HEVC decodes in software (1080p 10-bit keeps up); the P010 texture path is untested for that reason.

Design decisions worth knowing

  • The Mac app creates its own main window in applicationWillFinishLaunching. A SwiftUI Window scene doesn't create its window when the app is launched to open files (Finder "Open With").
  • Single-key shortcuts live in an event monitor, not menus, so typing in the playlist search field isn't hijacked.
  • The visualiser overrides video when on: video keeps decoding in sync but isn't drawn, so switching back is instant.
  • The 13 visualiser presets are original (MilkDrop-2 style: feedback warp, waveforms and shapes, blur glow, composite effects). projectM was considered and rejected; .milk files aren't loaded. --vis-snapshot <dir> renders every preset to PNG; that's how both ports were checked to match.
  • The Windows single-file build uses its own obj/bin. Sharing them with the normal build made the Windows App SDK reuse the wrong reg-free WinRT manifest ("ClassFactory cannot supply requested class").

10 · Build, test and safety rules

macOS build

  • Command Line Tools only (no Xcode), Swift 6.1 in Swift 5 mode, macOS 14+.
  • scripts/build_app.sh: per-arch swift build --triple, joined with lipo; fails if anything outside /System or /usr/lib is linked (checked with otool).
  • scripts/build_ffmpeg.sh: static, slim LGPL FFmpeg 9.0.2 per arch. Every demuxer and decoder; only ac3 + dca encoders and the spdif muxer.
  • An OPTIONS stamp (incl. a hash of the patches) triggers rebuilds. SwiftPM doesn't track the static libs, so delete product binaries after rebuilding FFmpeg.

Windows build

  • VS 2022 Build Tools (clang-cl 19, CMake, Ninja) + MSYS2 for make/nasm and test tools.
  • clang-cl because the engine uses C11 <stdatomic.h> (incl. _Atomic double); MSVC's C11 atomics are experimental.
  • build_ffmpeg_win.ps1: MSVC static FFmpeg, /MT, d3d11va/dxva2, same patches.
  • build_win.ps1 builds pcdump.exe; -App the WinUI app; -Package the single exe.

How correctness is checked

  • check_portable.sh (macOS): builds the core with the stub back-ends and fails on any OS media header or symbol.
  • pctest devices | play: headless playback on the real device with --seek, --pause-at, --then, --debug.
  • App debug: SURROUND_DEBUG logs status (and on Windows [trace …] breadcrumbs); --vis-snapshot renders the visualiser to PNG, since there are no screenshot permissions.
  • Memory bugs: Guard Malloc on pcdump found the FFmpeg DTS encoder bug (below).
Never play audible test signals. The TV is often the default output, and a test once played a 440 Hz tone through it. Anything that reaches a real device uses silent media (anullsrc). The rule applies to the Windows PC too. Success there is "the amp shows Dolby Digital, with no noise".
Never bitstream to analogue outputs. Back-ends must refuse IEC 61937 on speakers, headphones and Bluetooth; only HDMI, DisplayPort, S/PDIF or devices advertising a compressed format qualify.

Known limitations

  • DTS quality: FFmpeg's DTS encoder is experimental. A local patch fixes an out-of-bounds LFE history read (stock FFmpeg crashes ~1 in 12 runs). LFE still comes out ~2.8 dB low in the DTS path; cause not found.
  • Windows FFmpeg lacks zlib/bzlib: PNG cover art and zlib-compressed MKV tracks need zlib.
  • Not on Windows yet: HDR (PQ) tone mapping, proper cursor auto-hide.
  • Not implemented anywhere: subtitles, gapless playback, playlist persistence, E-AC3/TrueHD/DTS-HD bitstreaming to an HDMI AVR (the optical chain caps at AC3/DTS core anyway), notarization/signing.
  • Untested: DTS-HD sources (no encoder to make test files); whether the Samsung forwards DTS over optical.
  • Multichannel PCM follows FFmpeg's default channel order, not the device's preferred layout.

Suggested next steps

  1. Test Windows hot-plug with a real TV input change (silent file).
  2. Add zlib to the Windows FFmpeg build before relying on artwork.
  3. Watch for the start-up hang with SURROUND_DEBUG traces to confirm or rule out antivirus.
  4. HDR tone mapping and cursor auto-hide on Windows; then playlist persistence on both.
The one-sentence summary. Surround Player takes exclusive control of an HDMI output and streams Dolby Digital or DTS as IEC 61937 bursts, passed through or encoded on the fly. Portable C keeps the stream unbroken (whole bursts, encoded silence, a reused output) and drives video from the audio device's own clock, so a TV with only an optical link to the amp still delivers real 5.1.
